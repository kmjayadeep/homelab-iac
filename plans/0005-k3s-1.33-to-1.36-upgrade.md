# K3s 1.33 to 1.36 Upgrade Plan

Status: In progress (started 2026-10-28)

## Goal

Move the `titania` cluster from `v1.33.0+k3s1` to the current k3s stable
channel, `v1.36.5+k3s1`, one Kubernetes minor at a time, with the control
plane upgraded before the agents at every hop. Kubernetes 1.33 is past
upstream end of life (June 2026) and the version holds back two consumers in
`homelab-k8s`: Flux 2.10 requires Kubernetes >= 1.35 (`flux check` fails
today) and Longhorn 1.13 requires >= 1.34 (Renovate PR #395 is held).

## Current state (2026-10-28)

- Three nodes on `v1.33.0+k3s1`: `titania-master` (Debian 13, server),
  `titania-worker1` (Debian 13, agent), `titania-gpu` (Ubuntu 26.04, agent).
- k3s channels: `stable` = `v1.36.5+k3s1`, `latest` = `v1.37.1+k3s1`,
  `v1.34` = `v1.34.12+k3s1`, `v1.35` = `v1.35.9+k3s1`.
- Automatic etcd snapshots run twice daily on the master and are listed as
  `ETCDSnapshotFile` objects; a named snapshot was used before the overlayfs
  migration in July 2026.
- Longhorn 1.12.1: 20 volumes, all healthy, both storage nodes schedulable.
- Cilium 1.20.4 with `kube-proxy-replacement=false`; k3s runs its embedded
  kube-proxy in IPVS mode on the server.

## Compatibility review

- No installed Helm chart carries an upper `kubeVersion` bound (checked
  every HelmRelease against the upstream chart metadata).
- The apiserver `apiserver_requested_deprecated_apis` metric shows no API in
  use that is scheduled for removal; the Kubernetes deprecation guide lists
  no API removals in 1.33 through 1.37.
- Cilium 1.20.4 is e2e tested on Kubernetes 1.33 to 1.36. 1.37 is not listed.
- Longhorn 1.12.1 has no upper bound; Longhorn 1.13 lists 1.33 to 1.36 as
  tested and needs >= 1.34.
- Intel GPU device plugin 0.37.1 is built against Kubernetes 1.37.
- ingress-nginx 4.15.1 lists Kubernetes up to 1.35 as tested. The project is
  retired and ships no newer release, so 1.36 is an untested gap, not a
  blocker; the chart has no `kubeVersion` constraint.
- kube-proxy IPVS mode is deprecated from Kubernetes 1.35 (KEP-5495): a
  startup warning only. The `KubeProxyIPVS` gate defaults off in 1.40 and
  the code is removed in 1.43. Switching to nftables is follow-up work, not
  part of this plan.

## Design

- Follow the k3s manual upgrade procedure: replace `/usr/local/bin/k3s`,
  restart the service, no drain. k3s leaves running containers in place
  across a service restart, so workloads keep running while the kubelet is
  briefly NotReady.
- Hops: `v1.34.12+k3s1` -> `v1.35.9+k3s1` -> `v1.36.5+k3s1`. Stop at 1.36
  until Cilium and ingress-nginx list 1.37.
- Each hop:
  1. Named etcd snapshot on the master (`playbooks/etcd-snapshot.yml`).
  2. Bump `k3s_version` in `inventory/group_vars/k3s_masters.yml` and
     `inventory/group_vars/k3s_workers.yml`, commit.
  3. `playbooks/update.yml` (server). Wait for the node to report the new
     kubelet version and Ready.
  4. `playbooks/update-workers.yml` (agents, `serial: 1`). Wait for each
     node to report the new version and Ready before the next.
  5. Gate: all nodes Ready on the target version, no Flux resource not
     Ready, all pods Running or Completed, all attached Longhorn volumes
     healthy, Vault pods unsealed, the GPU trial pod still scheduled on
     `titania-gpu`, ingresses answer 200.
- Rollback for a failed server hop: stop k3s, restore the previous binary
  (k3s keeps none, so download the previous tag), and if etcd is damaged
  `k3s server --cluster-reset --cluster-reset-restore-path=<snapshot>`.
  Agents roll back by re-downloading the previous tag; agents must never be
  newer than the server.
